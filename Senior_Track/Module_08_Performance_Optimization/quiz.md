## Вопрос 6. Код: ленивая инициализация с Mutex

```kotlin
class LazyContainer<T>(private val factory: () -> T) {
    private var value: T? = null
    private val mutex = Mutex()

    suspend fun get(): T {
        return value ?: mutex.withLock {
            value ?: factory().also { value = it }
        }
    }
}
```

Зачем внутри `mutex.withLock` **снова** проверяется `value ?:`?

- **A)** Чтобы компилятор не ругался на nullable тип
- **B)** Чтобы не создавать значение повторно: несколько корутин могут дождаться мьютекса, и первая уже инициализировала `value`
- **C)** Чтобы каждый вызов `get()` возвращал новый объект
- **D)** Чтобы обнулить кэш перед созданием

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

Это классический double-checked locking. Первая проверка `value ?:` быстрая и без блокировки. Вторая — уже под мьютексом: пока корутина ждала лок, другая мог создать объект, и тогда factories вызывать нельзя. Без второй проверки тяжёлая зависимость (БД, сетевой клиент) создалась бы несколько раз, что убивает смысл lazy initialization при холодном старте.

**Почему не другие:**
- A — компилятор и так выведет тип; дело в логике гонки, а не в типах
- C — наоборот, контейнер должен вернуть **тот же** экземпляр
- D — обнуления здесь нет, `value` только устанавливается

</details>

## Вопрос 8. Код: утечка памяти в Compose

```kotlin
// ПЛОХО
@Composable
fun LeakyScreen() {
    LaunchedEffect(Unit) {
        while (true) {
            delay(1000)
            // Бесконечный цикл
        }
    }
}

// ХОРОШО
@Composable
fun OptimizedScreen() {
    LaunchedEffect(Unit) {
        // Работает только пока экран активен
    }
}
```

В чём, согласно модулю, проблема первого варианта?

- **A)** В нём отсутствует `remember`
- **B)** Бесконечный цикл держит корутину живой: её жизнь не ограничена активностью экрана, поэтому ресурсы не освобождаются
- **C)** `LaunchedEffect` нельзя использовать с `Unit`
- **D)** Нужно заменить `delay` на `Thread.sleep`

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

Модуль помечает первый пример как «ПЛОХО: корутин не отменяется при уничтожении экрана», а второй — как «ХОРОШО: корутин отменяется автоматически… работает только пока экран активен». Бесконечный `while (true)` с задержкой — типичная причина забытых корутин в списке memory leaks.

**Почему не другие:**
- A — `remember` здесь не решает проблему жизненного цикла корутины
- C — `LaunchedEffect(Unit)` — стандартный и корректный вызов
- D — `Thread.sleep` блокировал бы поток и был бы ещё хуже

</details>

## Вопрос 9. Найди ошибку (вопрос-ловушка)

```kotlin
class MemoryMonitor {
    private var monitorJob: Job? = null

    fun stopMonitoring() {
        monitorJob?.cancel()
        monitorJob = null
    }
}
```

Что не так в методе `stopMonitoring()`?

- **A)** Ничего, код корректный
- **B)** Нужно вызвать `monitorJob?.join()` вместо `cancel()`
- **C)** Нужно оставить `monitorJob` со ссылкой, иначе мониторинг не перезапустится
- **D)** Нужно обнулять `_memoryUsage` внутри этого метода

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: A** (код корректный!)

Это вопрос-ловушка: фрагмент дословно повторяет эталон из модуля. `cancel()` останавливает корутину мониторинга (цикл `while (isActive)` завершится), а обнуление ссылки не даёт «висеть» мёртвому `Job`. Повторный вызов `startMonitoring()` создаст новую задачу.

**Почему не другие:**
- B — `join()` ждёт завершения, но саму корутину не отменит; в примере используется именно `cancel()`
- C — наоборот, залипшая ссылка — это лишнее удержание объекта
- D — обнуление `_memoryUsage` в модуле не предусмотрено

</details>

## Вопрос 10. При каком пороге `CacheManager` чистит кэши?

- **A)** При превышении 100% лимита (150MB)
- **B)** При превышении 80% лимита (`usage > MEMORY_LIMIT_MB * 1024 * 1024 * 0.8`)
- **C)** При любом изменении `memoryUsage`
- **D)** Только по ручному вызову

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

В `init` блока `CacheManager` стоит:

```kotlin
memoryMonitor.memoryUsage.collect { usage ->
    if (usage > MEMORY_LIMIT_MB * 1024 * 1024 * 0.8) {
        clearCaches()
    }
}
```

То есть кэш чистится заранее — при 80% от лимита, до того как память станет критической. `clearCaches()` вызывает `clear()` у каждого `ClearableCache`.

**Почему не другие:**
- A — ждать 100% слишком поздно, пример использует коэффициент 0.8
- C — одного сбора недостаточно: условие — превышение порога
- D — очистка автоматическая, ручного вызова не требуется

</details>

## Вопрос 12. Как устроен `startMonitoring()` в `MemoryMonitor`?

- **A)** Выполняет однократное измерение и завершается
- **B)** Запускает корутину на `Dispatchers.Default` с циклом `while (isActive)`: читает usage, пишет в `StateFlow`, предупреждает при превышении лимита и ждёт `delay(periodMs)` (по умолчанию 1000 мс)
- **C)** Использует `Dispatchers.Main` и обновляет UI напрямую
- **D)** Вызывает Heap Dump каждую секунду

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

Код модуля:

```kotlin
monitorJob = CoroutineScope(Dispatchers.Default).launch {
    while (isActive) {
        val usage = getMemoryUsage()
        _memoryUsage.value = usage
        if (usage > MEMORY_LIMIT_MB * 1024 * 1024) logWarning(...)
        delay(periodMs)
    }
}
```

Значение публикуется в `StateFlow`, поэтому подписчики (в том числе Compose) получают обновления метрики. `periodMs` по умолчанию равен 1000.

**Почему не другие:**
- A — это непрерывный цикл, а не разовый замер
- C — используется `Dispatchers.Default`, а не Main; UI обновляется через сбор StateFlow
- D — Heap Dump делается вручную в Profiler, а не в рантайм-мониторе

</details>
