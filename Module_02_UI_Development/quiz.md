## Вопрос 1. Какой контейнер использовать, чтобы иконка «накладывалась» поверх текста?

- **A)** `Column`
- **B)** `Row`
- **C)** `Box`
- **D)** `LazyColumn`

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: C**

В модуле описаны три базовых контейнера:
- `Column` — элементы друг под другом (вертикально)
- `Row` — элементы друг за другом (горизонтально)
- `Box` — элементы **накладываются друг на друга** (именно он полезен для иконок поверх текста)

**Почему другие не подходят:**
- A — `Column` только расставляет элементы вертикально, наложения нет
- B — `Row` расставляет горизонтально
- D — `LazyColumn` это ленивый список, а не контейнер для наложения

</details>

## Вопрос 2. На экране 100 карточек, а лента потенциально бесконечная (как новостная). Что выбрать?

- **A)** `Column` — он проще и быстрее
- **B)** `LazyColumn` — он рендерит только те элементы, которые видны на экране
- **C)** `Row` с горизонтальной прокруткой
- **D)** `Box` со степенью `weight`

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

Прямое правило из модуля: «Если у вас 10 элементов — используйте `Column`. Если 100 или бесконечный список (как лента новостей) — **обязательно** используйте `LazyColumn`. Он рендерит только те элементы, которые видны на экране».

**Почему другие не подходят:**
- A — `Column` создаст все 100+ элементов сразу, что дорого по памяти и производительности
- C — `Row` не решает проблему объёма и меняет направление списка
- D — `weight` это модификатор, а не контейнер, и он не экономит рендеринг

</details>

## Вопрос 3. Найди ошибку во фрагменте экрана:

```kotlin
Scaffold(
    topBar = { TopAppBar(title = { Text("Привычки") }) },
    content = { paddingValues ->
        LazyColumn(
            modifier = Modifier.fillMaxSize()
        ) {
            items(habits) { habit ->
                HabitCard(habit = habit, onClick = { onHabitClick(habit.id) })
            }
        }
    }
)
```

- **A)** Ничего, код корректный
- **B)** Не передан `contentPadding = paddingValues` — контент будет скрыт под системными панелями
- **C)** `LazyColumn` нельзя использовать внутри `Scaffold`
- **D)** Нужно заменить `topBar` на `bottomBar`

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

Это ошибка №1 из раздела «Частые ошибки при работе с отступами». `Scaffold` автоматически учитывает статус-бар, notch, Dynamic Island и home indicator и отдаёт готовые отступы в `content`-лямбду как `paddingValues`. Их **обязательно** нужно применить:

```kotlin
LazyColumn(
    modifier = Modifier.fillMaxSize(),
    contentPadding = paddingValues // ✅
)
```

Без этого карточки окажутся под системными панелями. (Кстати, в рабочем коде модуля ещё используют `items(habits, key = { it.id })`, но отсутствие `key` — не ошибка, а улучшение.)

**Почему другие не подходят:**
- A — ошибка есть: отступы получены, но проигнорированы
- C — как раз наоборот: `Scaffold` + `LazyColumn` — рекомендованный связка из модуля
- D — `topBar` здесь уместен; дело не в нём, а в непереданных отступах

</details>

## Вопрос 4. Что делает `Spacer(modifier = Modifier.weight(1f))` в карточке `HabitCard`?

```kotlin
Row(
    modifier = Modifier.padding(16.dp),
    verticalAlignment = Alignment.CenterVertically
) {
    Icon(/* ... */)
    Spacer(modifier = Modifier.width(16.dp))
    Column { /* заголовок и категория */ }
    Spacer(modifier = Modifier.weight(1f))
    Text(text = habit.date)
}
```

- **A)** Добавляет отступ 16 dp между иконкой и текстом
- **B)** Забирает всё оставшееся пространство и прижимает дату к правому краю
- **C)** Делает дату невидимой
- **D)** Растягивает `Row` на всю высоту экрана

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

В коде `HabitCard` из модуля рядом с датой стоит `Spacer(modifier = Modifier.weight(1f))` с комментарием «Толкает дату вправо». Он занимает всё свободное место в `Row`, поэтому дата оказывается у правого края карточки. Отступ 16 dp — это **другой** `Spacer` (с `Modifier.width(16.dp)`), стоящий после иконки.

**Почему другие не подходят:**
- A — это работает `width(16.dp)`, а не `weight(1f)`
- C — `Spacer` не скрывает соседей, он только занимает место
- D — `weight` распределяет пространство вдоль оси `Row` (по ширине), а не по высоте

</details>

## Вопрос 5. Вопрос-ловушка. Что не так в этом коде type-safe навигации?

```kotlin
@Serializable
data class HabitDetailArgs(val habitId: String)

composable<HabitDetailArgs> { args ->
    HabitDetailScreen(habitId = args.habitId)
}

navController.navigate(HabitDetailArgs(habitId = "123"))
```

- **A)** Нужно использовать строковый маршрут `"habitDetail/{habitId}"`
- **B)** Не хватает ручного парсинга `NavBackStackEntry`
- **C)** Всё корректно — это и есть типобезопасная навигация
- **D)** В `composable` нужно добавить `override`

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: C** (код корректный!)

Это ловушка на «старый» подход. В модуле прямо описано, как было раньше: строковые маршруты вида `"profile/{userId}/{username}"`, опечатки, ручной парсинг из `NavBackStackEntry`, приведение типов, сериализация объектов в JSON-строку.

Сейчас (начиная с Navigation 2.8.0) каждый экран и его аргументы описываются Kotlin-классами с `@Serializable`, а переход выглядит как `navController.navigate(HabitDetailArgs(habitId = "123"))`. Типы проверяются на этапе компиляции.

**Почему другие не подходят:**
- A — строковые маршруты как раз устаревший способ
- B — ручной парсинг больше не нужен, `args.habitId` уже типизирован
- D — `composable` это DSL-функция, `override` здесь не нужен и не имеет смысла

</details>

## Вопрос 6. Для чего нужна аннотация `@Serializable` в навигации?

- **A)** Чтобы отправить данные экрана на сервер
- **B)** Чтобы пометить экран/аргументы для типобезопасной навигации: маршрут и аргументы проверяются компилятором
- **C)** Чтобы сохранить состояние экрана в базу данных
- **D)** Чтобы сделать `@Composable`-функцию потокобезопасной

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

По модулю: «каждый экран и его аргументы описываются с помощью Kotlin-классов или объектов, помеченных аннотацией `@Serializable`». Это ключ к type-safe навигации: `composable<HabitDetailArgs>` и `navController.navigate(HabitDetailArgs(...))` работают с классом, а не с строкой, поэтому ошибки ловятся при компиляции.

**Почему другие не подходят:**
- A — сериализация здесь служит навигации, а не сети
- C — БД в этом модуле ещё даже не подключена (это module 4)
- D — `@Serializable` ничего не говорит о потоках и `@Composable`

</details>

## Вопрос 7. Куда добавлять `androidx.navigation:navigation-compose:2.7.6` в KMP-проекте?

- **A)** В обычный блок `dependencies` корневого `build.gradle.kts`
- **B)** Только в `androidMain.dependencies`
- **C)** В `commonMain.dependencies` внутри блока `kotlin { sourceSets { ... } }` (или через `commonMainImplementation`)
- **D)** Только в `iosMain.dependencies`

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: C**

Модуль подчёркивает: «в Kotlin Multiplatform проектах зависимости должны добавляться в соответствующих sourceSets внутри блока `kotlin { ... }`, а не в обычный блок `dependencies`». Навигация нужна общему коду, поэтому она идёт в `commonMain.dependencies`:

```kotlin
kotlin {
    sourceSets {
        commonMain.dependencies {
            implementation("androidx.navigation:navigation-compose:2.7.6")
        }
    }
}
```

Альтернатива из модуля — `commonMainImplementation("...")` внутри блока `kotlin`.

**Почему другие не подходят:**
- A — обычный `dependencies` не даст зависимость в common-код KMP-модуля
- B — тогда навигация не будет доступна в `commonMain` (и не заработает на iOS)
- D — та же проблема, только наоборот

</details>

- **A)** Чтобы централизованно хранить версии и использовать алиасы вроде `libs.navigation.compose`
- **B)** Чтобы хранить SQL-запросы к базе данных
- **C)** Чтобы описывать SwiftUI-экран
- **D)** Чтобы генерировать `@Composable`-функции

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: A**

Version Catalog — «современный подход», рекомендуемый для новых проектов. В файле объявляются секции `[versions]`, `[libraries]`, `[plugins]`, а в `build.gradle.kts` используются алиасы: `implementation(libs.navigation.compose)`, `alias(libs.plugins.kotlin.serialization)`.

Преимущества по модулю: централизованное управление версиями, обновление в одном месте, отсутствие дублирования версий.

**Почему другие не подходят:**

- D — Composable-функции пишутся руками, каталог их не генерирует

## Вопрос 10. Чем отличаются `NavHost` и `NavController`?

- **A)** Это два названия одного и того же объекта
- **B)** `NavHost` — главный контейнер, управляющий экранами; `NavController` — объект, который переключает экраны через `navigate(...)`
- **C)** `NavHost` хранит тему, `NavController` рисует UI
- **D)** `NavController` создаётся автоматически внутри `NavHost`, его никуда передавать не нужно

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

Из раздела «Основные понятия навигации»:
1. `NavHost` — главный контейнер, который управляет экранами
2. `NavController` — объект, который переключает экраны (`navController.navigate("addHabit")`)

На практике `NavController` создаётся через `rememberNavController()` в `MainActivity` или `MainViewController` и передаётся в `AppNavHost(navController = navController)`.

**Почему другие не подходят:**
- A — это разные роли: контейнер и «дирижёр» переходов
- C — тема — это `MaterialTheme`, рисование — ответственность Compose
- D — `NavController` создаётся на платформе и явно передаётся в `NavHost`

</details>

## Вопрос 12. Как устроена темизация в модуле?

- **A)** Цвета (`ColorScheme`) определяются в `commonMain`; платформенные модули сообщают, когда применять тёмную тему; `EcoTrackTheme(darkTheme)` выбирает `DarkColorScheme` или `LightColorScheme`
- **B)** Цвета задаются только в iOS, Android использует системные
- **C)** `MaterialTheme` в KMP не используется, тема хранится в `SharedPreferences`
- **D)** Тема сохраняется в базе данных и загружается при старте

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: A**

В разделе про Material3 показан код:

```kotlin
@Composable
fun EcoTrackTheme(
    darkTheme: Boolean = false,
    content: @Composable () -> Unit
) {
    val colors = if (darkTheme) DarkColorScheme else LightColorScheme
    MaterialTheme(colorScheme = colors, content = content)
}
```

И пояснение: цвета определяются в `commonMain`, а в `androidMain`/`iosMain` система сообщает, когда применять тёмную тему. В домашнем задании нужно добавить `Switch` и менять переменную `darkTheme`.

**Почему другие не подходят:**
- B — цвета как раз общие, а не платформенные
- C — `MaterialTheme` используется, это основа темы
- D — про БД в этом модуле речи нет

</details>
