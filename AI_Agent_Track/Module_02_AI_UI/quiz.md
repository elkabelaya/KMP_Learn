## Вопрос 1. Какой раздел НЕ входит в структуру эффективного промпта для UI-генерации?

- **A)** Контекст (тип экрана, цель пользователя)
- **B)** Компоненты (Button, TextField, Card…)
- **C)** Ограничения (доступность, тёмная тема, локализация)
- **D)** Юнит-тесты для всех публичных функций

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: D**

В модуле приведена структура из пяти блоков:

```
Контекст: [тип экрана, цель пользователя]
Компоненты: [какие элементы нужны]
Стиль: [Material 3, кастомная тема, цвета]
Поведение: [клики, валидация, навигация]
Ограничения: [доступность, темная тема, локализация]
```

Тесты — отдельная тема (Модуль 4), в промпт для генерации UI они не включены.

**Почему другие не подходят:**
- A — это «Контекст», обязательный первый блок
- B — это «Компоненты», без них AI не знает, какие элементы рисовать
- C — это «Ограничения», именно тут задаются доступность и тёмная тема

</details>

## Вопрос 2. В чём суть few-shot prompting на примере `PrimaryButton` и `LoginForm`?

- **A)** Просить AI придумать стиль без единого примера
- **B)** Показать 1–2 готовых паттерна кода, а затем попросить сгенерировать новый экран «на основе этих паттернов»
- **C)** Перечислить только цвета и размеры шрифтов
- **D)** Сначала сгенерировать тесты, потом код по этим тестам

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

В модуле сначала показываются два образца — простая кнопка и форма с валидацией (`remember { mutableStateOf(...) }`, `OutlinedTextField`, `PasswordVisualTransformation`), а потом идёт строка: *«Теперь сгенерируй экран регистрации на основе этих паттернов…»*. Это и есть few-shot: AI видит нужный стиль, именование и структуру и продолжает в том же духе.

**Почему другие не подходят:**
- A — это zero-shot, а не few-shot; результат непредсказуемее
- C — одних цветов недостаточно, нужна структура кода
- D — это test-first подход, в теме 2.1 его нет

</details>

## Вопрос 5. Найди несоответствие промпту (ловушка):

```kotlin
val errors = remember(activityType, distance) {
    buildList {
        if (activityType == null) add("Выберите тип активности")
        if (distance.isBlank()) add("Укажите дистанцию или вес")
        if (distance.toDoubleOrNull() == null) add("Некорректное значение")
    }
}
```

Какая проверка, описанная в промпте, здесь реально отсутствует?

- **A)** Дата не в будущем
- **B)** Проверка, что тип активности выбран
- **C)** Проверка, что дистанция не пустая
- **D)** Проверка, что значение — число

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: A**

Это вопрос-ловушка: код выглядит «валидным», но `errors` зависит только от `activityType` и `distance`. Переменная `date` есть в состоянии и передаётся в `DateTimePicker`, однако условие «дата не в будущем» в `buildList` не попало — будущая дата пройдёт валидацию.

> 💡 Бонус: обрати внимание, что и «дистанция/вес > 0» здесь не проверяется — `toDoubleOrNull()` пропускает отрицательное число.но такая проверка не предложена в вариантах ответа.

**Почему другие не подходят:**
- B — есть: `if (activityType == null)`
- C — есть: `if (distance.isBlank())`
- D — есть: `if (distance.toDoubleOrNull() == null)`

**Практический вывод:** сгенерированный AI код нужно сверять с промптом построчно — «выглядит правдоподобно» ≠ «реализовано».

</details>

## Вопрос 10. Что делает строка `sweepAngle = 360f * animatedProgress` в `ProgressRing`?

- **A)** Рисует полный круг независимо от прогресса
- **B)** Заполняет дугу от 0° до 360° пропорционально `progress` (0.0…1.0)
- **C)** Поворачивает кольцо на 90 градусов
- **D)** Задаёт радиус кольца

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

В коде фоновое кольцо рисуется с `sweepAngle = 360f`, а кольцо прогресса — с `sweepAngle = 360f * animatedProgress.value`. При `progress = 0.5` заполняется 180°. `startAngle = -90f` просто ставит начало сверху, а `useCenter = false` означает, что рисуется дуга, а не сектор (без заливки до центра).

**Почему другие не подходят:**
- A — полный круг — это фоновое кольцо
- C — `-90f` задаёт стартовый угол, а не sweepAngle
- D — радиус считается отдельно: `val radius = center - 8f`

</details>

## Вопрос 14. В чём неочевидный минус кэширования в этом коде (ловушка)?

```kotlin
val cacheKey = normalizeMessage(message)
if (cache.containsKey(cacheKey)) {
    return ChatResponse(content = cache[cacheKey]!!, isCached = true)
}
// ...
private fun normalizeMessage(message: String): String =
    message.lowercase().replace(Regex("\\s+"), " ").trim()
```

- **A)** Ключ кэша учитывает только текст сообщения и игнорирует историю диалога
- **B)** Кэш хранится в SQLDelight и замедляет ответы
- **C)** Кэш отключает system prompt для всех запросов
- **D)** Кэш работает только для сообщений длиннее 100 символов

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: A**

`normalizeMessage` приводит текст к нижнему регистру, схлопывает пробелы и обрезает края. Но в ключ **не входит история**: `chat(message, history)` может быть вызван с разной историей, а ответ будет взят из кэша по одному и тому же тексту. Для чат-бота это риск дать одинаковый ответ в разных контекстах.

**Почему другие не подходят:**
- B — кэш это `MutableMap<String, String>` в памяти, не БД
- C — system prompt добавляется в `messages` при каждом некэшированном вызове
- D — ограничения по длине в коде нет

</details>

## Вопрос 15. Зачем в оптимизированном `UserList` указан `key = { user -> user.id }`?

- **A)** Для сортировки пользователей по id
- **B)** Чтобы Compose мог точечно обновлять и переиспользовать элементы при изменении списка
- **C)** Для связи с базой данных
- **D)** Для запуска анимации появления

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

В «до»-версии `Column { users.forEach { UserCard(...) } }` изменение списка вызывает recomposition всех карточек. В «после» — `LazyColumn { items(items = users, key = { it.id }) { ... } }`: ключ позволяет Compose понять, какой именно элемент изменился, и перерисовать только его. Дополнительно `derivedStateOf` используется для вычисляемого `isOnline`, чтобы не пересчитывать состояние при каждой recomposition.

**Почему другие не подходят:**
- A — ключ ничего не сортирует, порядок задаётся списком
- C — в оптимизации производительности БД не участвует
- D — анимации — отдельная тема (в Dashboard это `AnimatedVisibility`)

</details>
