## Вопрос 1. В какой роли выступает AI в шаблоне промпта для проектирования архитектуры?

- **A)** Junior Developer, который пишет код по готовому ТЗ
- **B)** Principal Architect с 10+ годами опыта в мобильной разработке
- **C)** QA Lead, который ищет непокрытые ветви
- **D)** Product Manager, который формирует бэклог

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

Шаблон начинается со строки: *«Ты — Principal Architect с 10+ лет опытом в мобильной разработке»*. Затем задаётся контекст (приложение, платформы Android/iOS/Desktop на KMP, нагрузка, критические требования) и задача — спроектировать архитектуру с Clean Architecture.

**Почему другие не подходят:**
- A — роль junior не даёт права обосновывать архитектурные решения
- C — QA Lead — роль из Модуля 4 (анализ coverage)
- D — PM не проектирует модульную структуру и DI

</details>

## Вопрос 3. В каком модуле структуры e-commerce лежит «SQLDelight setup, migrations»?

- **A)** `:core-network`
- **B)** `:core-db`
- **C)** `:feature-products`
- **D)** `:domain-models`

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

В сгенерированном дереве `:shared/:core/` содержит четыре модуля:
- `:core-common` — Result, Either, extensions
- `:core-network` — Ktor client, interceptors
- `:core-db` — SQLDelight setup, migrations
- `:core-designsystem` — Material 3 тема, компоненты

**Почему другие не подходят:**
- A — `:core-network` отвечает за сеть (Ktor)
- C — `:feature-products` — каталог, поиск, фильтры
- D — `:domain-models` — entities и value objects

</details>

## Вопрос 4. Что входит в «вертикальный срез» фичи при Feature-First Modularization?

- **A)** Только UI-слой
- **B)** domain/, data/, ui/ внутри одного feature-модуля
- **C)** Только общие утилиты и extensions
- **D)** Отдельные модули по слоям без привязки к фичам

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

В примере указано: `feature-products/ → domain/ (UseCases, entities), data/ (Repository implementations, local/remote), ui/ (Compose screens, viewModels)`. Преимущества: независимая компиляция и тестирование, масштабирование команд, чёткие границы владения.

**Почему другие не подходят:**
- A — один UI не образует срез, бизнес-логика и данные потеряны
- C — это `:core-common`, а не фича
- D — это Layer-First, противоположный подход; в примере выбран Feature-First

</details>

## Вопрос 5. Какой порядок описывает Unidirectional Data Flow в модуле?

- **A)** State → UI → Event → ViewModel → State
- **B)** UI → Event → ViewModel → State → UI
- **C)** ViewModel → UI → Event → State → ViewModel
- **D)** Event → State → UI → ViewModel → Event

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

В модуле записано: `UI -> Event -> ViewModel -> State -> UI`. Преимущества: предсказуемое управление состоянием, простота тестирования и отладки, единый паттерн для всех фич.

**Почему другие не подходят:**
- A — состояние не может быть источником события до ввода пользователя
- C, D — нарушают замкнутый цикл «событие → обработка → новое состояние → рендер»

</details>

## Вопрос 6. Что является source of truth в offline-first стратегии и как разрешаются конфликты?

- **A)** Сервер; конфликты всегда решаются на сервере
- **B)** Локальная БД; background sync, last-write-wins + ручное разрешение для критичных данных
- **C)** Память процесса; конфликты игнорируются
- **D)** Локальный кэш HTTP; всегда побеждает сервер

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

В архитектурном решении №3: локальная БД как source of truth, фоновая синхронизация с сервером, `last-write-wins` плюс ручное разрешение конфликтов для critical data.

**Почему другие не подходят:**
- A — при offline-first главный источник данных локальный, иначе офлайн-режим не работает
- C — память процесса не переживает перезапуск приложения
- D — HTTP-кэш не заменяет полноценную БД и не решает конфликты записи

</details>

## Вопрос 7. Какое соответствие технологий из стека неверно?

- **A)** DI — Koin; DB — SQLDelight
- **B)** Network — Ktor Client; State — StateFlow + MVI
- **C)** DI — SQLDelight; DB — Koin
- **D)** Koin выбран как лёгкий фреймворк с хорошей поддержкой KMP

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: C**

В стеке: DI — Koin (lightweight, good KMP support), DB — SQLDelight (type-safe queries, multiplatform), Network — Ktor Client (unified HTTP API), State — StateFlow + MVI. Вариант C переставляет DI и БД местами.

**Почему другие не подходят:**
- A, B — корректные пары из раздела «Technology Stack»
- D — дословное обоснование выбора Koin из модуля

</details>

## Вопрос 9. Какого раздела НЕТ в шаблоне ADR?

- **A)** Статус и контекст
- **B)** Решение и последствия (положительные/отрицательные)
- **C)** Альтернативы с объяснением, почему не выбраны
- **D)** Список юнит-тестов и процент coverage

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: D**

Шаблон ADR содержит: `# [ADR-001] Название`, `## Статус`, `## Контекст`, `## Решение`, `## Последствия` (положительные и отрицательные), `## Альтернативы`, `## Ссылки`, дату и автора. Тесты и coverage — не часть ADR.

**Почему другие не подходят:**
- A, B, C — обязательные секции стандартного формата

</details>

## Вопрос 10. Какой статус НЕ предусмотрен в шаблоне ADR?

- **A)** Proposed
- **B)** Accepted
- **C)** Deprecated
- **D)** In Progress

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: D**

Допустимые значения: `Proposed | Accepted | Deprecated | Superseded`. `In Progress` в шаблоне отсутствует — незавершённое решение описывается как Proposed.

**Почему другие не подходят:**
- A, B, C — все три приведены в шаблоне; четвёртый валидный статус — Superseded

</details>

## Вопрос 12. Что предлагается сделать с монолитной функцией (ловушка на число шагов):

```kotlin
// Monolithic function - 150+ строк
suspend fun processOrder(orderData: String): Boolean {
    // Parsing, validation, DB operations, API calls, notifications
}
```

- **A)** Оставить как есть: 150 строк — нормальная длина для одной функции
- **B)** Разделить на 5 функций: ParseOrderInput, CreateOrderUseCase, SaveOrderLocally, SyncOrderToServer, SendNotifications; каждая ≤ 30 строк
- **C)** Разделить на 3 функции: parse, save, send
- **D)** Просто переименовать функцию и добавить KDoc

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

В промпте для рефакторинга прямо перечислены пять ответственностей и требование: каждая функция ≤ 30 строк с чёткой ответственностью. Это применение Single Responsibility Principle. Общий шаблон рефакторинга дополнительно просит снизить cyclomatic complexity, устранить дублирование, улучшить naming, добавить KDoc и улучшить error handling.

**Почему другие не подходят:**
- A — 150+ строк с пятью разными задачами нарушают SRP
- C — три функции не покрывают парсинг/валидацию и синхронизацию по отдельности
- D — переименование не уменьшает сложность и не разделяет ответственности

</details>

## Вопрос 13. Что анализирует шаблон оптимизации структуры проекта (роль Staff Engineer)?

- **A)** Только цветовую схему приложения
- **B)** Циклические зависимости, узкие места сборки, feature-first vs layer-first, долю общего кода
- **C)** Только количество экранов в UI
- **D)** Только тексты локализации

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

Шаблон предлагает анализировать: 1) module dependencies (циклические зависимости?), 2) build time bottlenecks, 3) code organization (feature-first vs layer-first), 4) shared code percentage. На выходе: новая структура с обоснованием, пошаговый миграционный план, ожидаемые улучшения (build time %, maintainability score) и Mermaid-диаграмма до/после.

**Почему другие не подходят:**
- A, C, D — эти вопросы не входят в шаблон оптимизации структуры; практическое задание 3.3 требует ускорения build time на 20%+

</details>

## Вопрос 14. AI выбрал Koin в ADR. Можно ли сразу применять решение без дополнительной проверки (ловушка)?

- **A)** Да — AI выступил в роли Technical Lead, значит решение авторитетно
- **B)** Нет — слепое доверие рекомендациям — ошибка; нужно проверить соответствие требованиям и явно запросить trade-offs
- **C)** Да — если в ADR есть раздел «Альтернативы»
- **D)** Нет — нужно переписать ADR вручную без участия AI

<details>
<summary>💡 Показать ответ и объяснение</summary>

**Правильный ответ: B**

В разделе «Ошибки при использовании AI для архитектуры» прямо названы: слепое доверие рекомендациям (решение — всегда проверять соответствие вашим требованиям), игнорирование trade-offs (решение — просить AI явно описывать компромиссы), отсутствие контекста (решение — давать полный контекст: команда, сроки, бюджет, constraints). Роль в промпте — это стиль ответа, а не гарантия правильности.

**Почему другие не подходят:**
- A — авторитетность роли не отменяет проверки
- C — наличие раздела «Альтернативы» не заменяет критическую оценку
- D — AI можно и нужно использовать, вопрос в проверке результата, а не в отказе от инструмента

</details>
